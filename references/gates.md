# 决策、权限与证据门

使用本页任何门前，先读并执行[公共合同](execution.md#common-contract)，包括独立审阅或门控动作前的余量检查；再读本页当前事件的完整规则单元。

## 可以直接继续

在已接受范围内，Harness 可以：

- 只读检查仓库、环境、依赖、许可证和运行状态；
- 查询当前一手资料；
- 完成可逆的本地编辑、测试、排错和文档更新；
- 选择不改变产品行为或风险的普通实现细节；
- 安装已获批准、回滚方式明确的项目依赖；
- 修复通过已接受测试和门槛所必需的问题；
- 更新节点状态，激活下一节点；
- 在本地提交已验证且范围清楚的变更。

## 遇到重大决策时停止

以下情况需要用户选择：

- 目标、用户、范围或验收标准发生实质变化；
- 架构将改变持久数据、隔离、隐私、权限、互操作性或长期运行方式；
- 工具带来持续费用、限制性或不明确的许可证、遥测、云端数据传输或供应商锁定；
- 要求互相冲突，且没有安全、可逆的默认选项；
- 新的真实证据推翻了已接受设计。

停止时给出证据、可选方案、取舍、建议，以及一个需要用户回答的明确问题。

## 遇到权限边界时停止

- 安装或修改全局插件、Skill、Hook、受信任程序或持久机器配置；
- 请求凭据、令牌、账号变更、付费服务或超出既定边界的数据传输；
- 执行未获授权的远端推送、PR、发布、生产部署、外部消息或第三方协调；
- 因连接器或 CLI 能力不足改用用户浏览器登录态，但用户尚未允许；
- 执行破坏性或难以恢复的文件、数据库、迁移、历史或基础设施操作。

请求应尽量小，并说明动作、目标、持久性、外部影响和回滚。权限被拒绝后不得绕过。

## 复用同一节点的授权

同一活动节点内，用户已明确批准的同类动作不重复询问。复用仅适用于目标、动作类别、数据类别、成本范围、持久性和外部影响均未改变的后续动作。

不得把一次授权推广到不同类别的新数据或新成本范围。出现新数据类别、任何新增或扩大成本、不同的外部接收方、持久性变化、权限扩大时，必须核对新授权；转入新节点先复核既有授权，若用户已明确批准整体计划且动作仍在其范围内则继续，不重复询问。授权措辞不清楚时，按未获授权处理。

## 证据登记、条件授权与副作用

触发：收到用户截图、原件、人工决定或外部结果。动作：在覆盖层解析的唯一活动状态（默认 `.delivery/state.md`）先登记最小证据回执，再分析、设计或执行副作用。方法：写 `received_at`、`source_ref`（不可持久保存则 `needs-source`）、范围、直接观察、限制和未决；只有获授权时才复制原件到证据槽。判据：后续结论能追溯到来源，事实与推断分开。失败：标记 `needs-source`，不得把推断写成已证实事实。证据：回执本身及获授权的证据槽引用。

新证据先登记最小回执；完整回执归入唯一证据来源后，state 只保留仍影响当前动作的结论、限制和精确入口，按[文档生命周期](context-lifecycle.md)收敛。

新会话或新活动节点复用既有用户或外部证据，也触发本门；若旧回执缺少 `source_ref` 或 `needs-source`，先补录，随后才能用它支持实施、部署或外部写入。

授权类别必须分开：证据登记、可逆本地实验、远端部署或服务重启、外部持久数据写入、导入/激活/发布。前一类不授权后一类。`先检查并反馈`、`检查后再继续` 等条件性措辞只授权检查和反馈；报告已被用户接收并明确同意下一动作前，不得实施、部署或写入外部状态。

预实验即使已部署也不是完成。登记目的、变更版本、未证明的验收条件、回滚和禁止推导的结论；未满足已批准设计时，不得称为“已上线”、实现完成或后续导入/激活的依据。

## 遇到证据门时停止

- 必需的真实样本、设备、浏览器状态、用户行为、数据集、账号、服务或类生产环境不可用；
- 完整验证命令失败；
- 只有削弱验收标准才能让测试通过；
- 准确率、延迟、隐私、安全或可靠性门槛无法测量。

此时不能把阶段标为完成。记录现有证据、缺失证据、已经穷尽的安全工作，以及准确的解除条件。

## 停止时写出一行可见理由

停止的回复里必须写出一行停止理由，只能从封闭清单选择：

```text
停在这里，因为：<等用户决断 / 等用户机器上的执行结果 / 等必要证据或在途操作结果 / 需要新授权 / 需求有多种合理解释需先厘清>
```

写不出来就不许停，包括刚刚宣布了要做某事的时候。这一行不是闸门而是可见性机制：它把「零产出但消息正常」变成「该有的那行理由不在」。验收标准不是「不再过早停止」，而是「每次停止都能被一眼判断有没有道理」。

用户若另有节奏偏好，那约束的是交接的内容（一次给几组命令），不是回合边界。两件事混同会产生「用一句『我现在开始做』当交接然后停下」的稳态。

<a id="formal-record-consistency"></a>
## 正式记录一致性与完成门

触发：执行需维护正式记录的持久变更、部署、发布或补登前，以及本批验收或完成声明前。
从项目契约解析权威来源、作用域、记录含义、写入方与时机、前后核验和恢复入口；
未映射时先按[初始化](project-initialization.md#formal-records)定位原生机制，不以“未声明”推定不适用。

| 记录含义 | 执行前判据 | 完成判据 |
|---|---|---|
| 已发生事实或当前状态账 | 对本动作所需基线的陈述与实际相符，无相关漏记、冲突或未知结果 | 本批目标效果与应有记录一致，身份、结果和权威回读齐备 |
| 目标声明 | 目标已接受并绑定精确产物，允许从当前基线到目标；两者此时可以不同 | 实际达到目标，不反向修改目标使未完成通过 |
| 事件记录 | 按操作标识核验必要前序与在途状态，不以全表末行代表本操作 | 本操作所需事件及结果符合协议；受理、开始或其他操作的成功不代表本操作完成 |

方法：固定对象、环境、产物和本批范围，使用原生执行、登记及回读入口；自定义、受限或人工路径承担相同义务。
按项目模型核验相关记录的身份、内容、依赖、有效状态和实际效果，不能只比较末行、最大编号或仓库最新文件。
有并发写入时沿用原生锁、版本条件或临执行复核，不能自动接受已漂移的基线。
执行前通过只允许开始；本批效果、应有记录和回读满足后置条件才可关闭完成门。
同批闭合不强求同一数据库事务；非原子或异步协议中的部分完成、待确认结果按项目阶段门处理，不能直接记成功。

失败：相关遗漏、冲突或未知结果使受影响写入与依赖门保持关闭；state 保留当前结论、唯一恢复动作与证据入口。
“欠账保留”、退出码为零或把残留值写成 expected 均不构成放行。只读核实、已有授权内恢复和独立安全工作可继续。
补登须同时有覆盖该写入的授权和足够事实证据；仅补可证明的范围并回读，未知原执行时间不能用补登时间伪造。
按[恢复合同](context-lifecycle.md#recovery)先核实原操作；不盲目重放，不通过改写已执行工件或历史来掩盖差异，不无证据补记成功。
已有授权覆盖就继续；缺必要决策、权限或证据才请求用户，批准修复本身不表示差异已消除。

证据：在既有批次回执保存契约来源、对象/版本、前后判据、相关记录标识、方法、结果、限制及恢复入口。
过程只索引，活动状态不复制台账；不另建平行记录或逐动作全量扫描。确定性阻断由项目真实执行入口承担。

<a id="write-back-check"></a>
### 落笔自检

触发：写入或更新唯一活动状态、证据回执、过程记录、覆盖层或任何将作为交付依据的正式记录后；宣告完成、交接或提交前。

动作：立即读回刚写入的实际内容，而不是信任写入命令的退出码、编辑器的保存提示或记忆中的草稿。

判据：回读内容与写入意图一致：字段、路径、编号、链接、授权范围和结论都在；没有漏行、截断、乱码、编码错误，也没有写到别的路径或别的记录面。

失败：视为该记录未完成：不声明完成、不提交、不以未回读的记录作为证据继续。修复后再次读回，直到一致；无法确认写入目标时，记录具体路径、现象与解除条件后停止。

证据：回读时间、读取路径与位置、一致或不一致的结论；不复制敏感值。

## 提交、远端发布与脱敏门

### 记录与身份可用性门

触发：首次执行本次交付变更的 `git add` 前。动作：确认唯一活动状态、项目覆盖层和过程记录均可读，且既有记录体系可在提交前保存必要回执并更新索引；同时读出可用的作者身份策略。方法：用项目覆盖层声明的路径做最小读写预检，不读取证据槽内容；再比较 `git var GIT_AUTHOR_IDENT` 与作者策略。判据：记录已更新、身份策略可用且候选身份一致。失败：**不得暂存、提交或推送**，不得从当前 Git 身份、旧提交或远端作者猜测策略；把记录路径失败设为活动诊断节点，依次做一次限定时长的最小读取、一次等价只读重试和一次不覆盖原记录的写入预检。不得擅自迁移记录、创建替代记录面或把超时说成记录成功。三次安全检查仍失败时，保留未暂存变更，报告具体路径、操作、超时/错误和解除条件，再停止。证据：路径、预检时间、写入结果、身份策略来源和比对结论；不记录敏感值。

<a id="mechanical-preflight"></a>
### 机械预检门

触发：本次交付变更首次执行 `git add` 前；任何完成、交接或发布声明前；安装提交 hook 后每次提交时（`--staged --message-file`）。

动作：在项目根运行[机械预检](preflight.md)（`python -B -X utf8 <skill>/references/preflight.py --root . --json`；提交前加 `--staged`，候选消息用 `--message-file`，提交后加 `--readback`），按项目配置核对记录可用、记录与代码同批、证据链接与编号、baseline、记录体量、秘密、候选消息与身份。

判据：退出码 0，且没有 block 级失败；warn 与 skip 逐项登记，其中身份策略缺失、记录未纳入版本控制等 skip 不构成对应门通过。

方法：先跑预检再暂存；失败按输出修复建议处理。预检不自动修改记录，也不得为通过而创建替代记录面。hook 是可选项且需显式同意；未安装 hook 时由执行者在同一执行点运行同样命令。

失败：退出码 1 等同对应门失败，不得 `git add`、提交、推送或宣告完成；先修复记录、证据、消息或身份，或按豁免文件写明理由后复验。退出码 2 为用法或配置错误，同样不得继续，不得用猜测配置绕过。

例外：`--no-verify` 只限 hook 环境不可用或紧急恢复，须在过程记录写明原因并在提交后补跑 `--readback` 与其他证据；检查本身失败时禁止绕过。重复绕过视为门失败。

证据：预检命令、退出码、`--json` 摘要、`config_source`、豁免依据与回读结果；不记录秘密值与会话链接。

<a id="commit-history-coverage"></a>
### 检查范围与历史覆盖

提交前检查当前工作树、暂存区、候选消息和历史覆盖。范围至少包括私钥、令牌、密码、云凭据、连接串、认证文件、会话 Cookie、真实个人信息、机器专属路径，以及带身份或权限信息的命令输出。

首次接入或无可信基线时，完整检查项目要求覆盖的历史。回执绑定可核验的对象集合/边界、引用范围、规则与工具版本、结果及限制。
后续检查全部新增、改写、引入且未被有效基线覆盖的对象；仅复用已覆盖且未变化对象的结果，不因时间经过机械重扫。
规则变化、范围扩大、历史导入/改写或基线不可核验时补检受影响范围；无法证明覆盖边界时扩大至必要全量检查。
推送或发布前，确认拟发布的完整对象范围已被当前有效规则覆盖；基线不替代当前工作树、暂存区和候选消息检查。

提交元数据同样在覆盖范围内。只扫描文件内容查不到消息、作者和提交者身份，须单独核验；不能把检查过某个旧 HEAD 当作完整覆盖。

触发：执行 `git commit` 或其他创建/改写提交的入口前。动作：检查候选提交消息的标题、正文和 trailer，不只扫描既有历史。候选提交消息来自 `-m`、`-F`、编辑器或 Agent 自动生成时都一样处理。会话、分享、聊天或其他不透明协作链接不得写入提交元数据；`Claude-Session` 一类 trailer 也不得写入提交元数据。

方法：先把将要提交的精确文本作为草稿审阅，重点检查 URL、`session`、`share` 和平台名组合；只保留解释变更所必需的、领域中立的文本。判据：候选消息不含会话/分享链接或其 trailer，且不依赖链接才能理解。失败：中止本次提交，删除链接或改写为中立原因，重新检查；若已推送，按历史暴露流程记录并请求清理方案的明确授权。证据：记录检查时间、消息来源、命中类型和处置，不记录链接值。

<a id="commit-object-readback"></a>
### 提交对象回读

触发：提交被创建、改写或引入后，在依赖这些对象续行、交接或推送/发布前。
按实际 SHA 读回消息、作者与提交者等受策略约束的元数据，核对候选内容、身份策略和交付对象。
普通提交检查本次对象；amend、rebase、cherry-pick、merge、squash 或导入检查全部受影响且未覆盖的新对象，不只检查最终 HEAD。
检查回执绑定对象集合与规则版本；对象改变后旧回执不覆盖新对象，最终消息不能仅凭候选草稿或工具成功提示认定合格。
发现问题时暂停受影响后续动作，按既有授权和历史改写边界修复后复验；记录对象标识、命中类型及处置，不复制被禁止的值。

提交前先确认本次提交实际生效的身份，不要假设它等于项目策略。身份由当前会话与运行时的环境决定：仓库自身可能没有配置，全局配置可能属于另一个用途，运行时也可能通过环境变量注入自己的身份。跨项目、跨运行时或换一台机器继续同一个仓库时，生效值会跟着变，而没有任何环节会提醒你它变了。

做法是提交前读出生效值并与项目覆盖层的作者身份策略核对。`git var GIT_AUTHOR_IDENT` 会把配置与环境变量注入一并算进去，未配置时直接报身份未知。不一致时用单次提交级参数覆盖，例如 `git -c user.name=... -c user.email=... commit`，不修改用户的全局配置。

身份变化须核对适用策略与检查回执；多位获准贡献者本身不证明漏检。

不得提交真实秘密作为测试样本。测试只能使用明显无效的占位值，并避免采用会被误认为可用凭据的完整格式。扫描工具可用时使用专用秘密扫描器；不可用时使用仓库搜索和 Git 对象检查作为降级，并明确覆盖限制。

发现秘密时：

1. 立即停止提交和推送，不在回复、日志或修复提交中重复秘密。
2. 先撤销或轮换可能仍有效的秘密，再清理当前文件。
3. 已进入 Git 历史的秘密不能靠普通新提交删除。需要选择历史重写、建立干净的新根提交或新仓库。
4. 历史重写、删除旧远端引用和强制推送会影响协作者，属于破坏性远端操作。必须说明备份、影响、重新克隆要求和验证方法，并取得明确授权。
5. 已经推送到公开托管平台的历史，重写加强制推送不足以清除。旧提交仍可按 SHA 访问，也留在克隆、复刻和 PR 引用里。要真正清除需要平台侧介入或删除并重建仓库；决定前先向平台一手文档核实当前行为。
6. 完成清理后重新扫描工作树、暂存区、全部分支和标签，再创建全新提交。

如果只发现公开用户名、公开仓库地址或文档示例，不要误报为秘密。账号标识是否需要匿名化由项目公开范围决定。扫描报告只记录文件、提交、秘密类型和处置状态，不保存秘密值。

## 独立审阅失败恢复门

触发：独立审阅报告 Critical 或 Important 发现。动作：把该发现设为唯一活动节点，复现、最小修复并重新独立审阅；继续禁止未通过门所保护的部署、外部写入、导入、激活或发布。方法：记录发现、受影响范围、复现命令、修复与重审证据；在长验证或重审前确认运行余量，余量不足或不可确认时先记录可恢复交接（活动发现/证据、已完成验证、冻结副作用、唯一恢复动作、解除条件）。判据：发现被复现并修复，相关测试和复审通过。失败：只有新决策、新权限或真实证据缺失时暂停，并写出本门规定的可见停止理由及解除条件；额度耗尽不等同完成。证据：审阅报告、复现、修复和重审记录。

未解决的 Critical/Important 发现不得成为活动节点的最后一项工作或把会话标为完成；审阅发现本身不是暂停理由。

## 最终审阅新鲜度门

触发：一次独立审阅后，代码、运行配置或交付包发生变化。动作：在部署、发布或完成声明前，对最终产物重新独立审阅。判据：审阅对象与将部署、发布或宣称完成的精确版本一致。失败：旧审阅、测试、扫描、自审或旧版本现场验证均不通过本门；已部署旧版本时，记录版本差异，不把旧现场结论用于新版本。证据：最终版本标识和新的独立审阅记录。

### 输出脱敏（运行诊断、探针或状态命令时）

工具输出会原样进入会话与持久记录。运行可能接触凭据的命令（探针、状态检查、日志查看、读配置）前，先核对输出遮蔽策略：凭据值脱敏后才进入上下文，值不得原样出现，键名与结构可留。判据：此类输出不含真实凭据值。诊断结果**默认不落盘**；确需归档时，先脱敏，再写入用户批准且权限合适的位置，并登记保存期限。落槽不等于安全：项目状态区可能被文件同步，含凭据值的内容不得因落入槽位而免于脱敏；槽位不是秘密保险箱，归档也须先脱敏。

发现输出已含真实值（即使脚本声称已遮蔽），按「已泄露」处置：

1. 不重复值：回复、日志、记录中不复制真实值。
2. 立即列入轮换：已泄露的密钥、令牌列入轮换清单，轮换执行须授权。
3. 清理残留：删除落到临时文件、服务器文件的泄露副本并复核。
4. 登记：记录泄露面（哪些会话/文件/机器）、处置与残余。

### 通用性检查

秘密扫描之外还有一道独立检查，两者范围不同，不能互相替代。上面那条「不要误报为秘密」只约束秘密扫描，不豁免这一道。

这**不是安全问题**，是可复用性问题。通用 Skill 带着某一个项目的世界走，会污染它服务的其它每一个项目。判据不是「会不会泄密」，而是：**把这个仓库交给一个完全不相干的项目，读起来会不会莫名其妙。**

范围：用户的基础设施名称、同步工具、服务器主机名、产品名、仓库名，以及只属于某个项目的业务领域词汇。

方法分三层，因为单靠任何一层都不够：

1. 通用形态用测试自动扫描：私有网段地址、用户目录路径、邮箱。写成测试而不是清单，扫描器本身才不会变成泄漏点。
2. 具名词用项目覆盖层的禁用词清单。这些词本身就是项目事实，不写进通用仓库。
3. 领域词汇只能人工过。本次新增或改写的经验条目、示例和触发场景逐条确认领域中立：写清失败模式和判据，不写它发生在哪个业务上。**秘密扫描抓不到它，正则也抓不到它**，只有读一遍能抓到。

发现时不按秘密流程处理：不需要轮换，不需要停止一切。改写成领域中立描述或占位符，重跑测试，正常提交。已进入 Git 历史的，历史重写仍是独立权限门；重写前先确认文档里有没有引用提交 SHA，重写会让这些引用全部失效。
