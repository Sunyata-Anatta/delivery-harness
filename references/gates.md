# 决策、权限与证据门

## 可以直接继续

在已接受范围内，Harness 可以：

- 只读检查仓库、环境、依赖、许可证和运行状态；
- 查询当前一手资料；
- 完成可逆的本地编辑、测试、排错和文档更新；
- 选择不改变产品行为或风险的普通实现细节；
- 安装已获批准、回滚方式明确的项目依赖；
- 修复通过已接受测试和门槛所必需的问题；
- 更新节点状态，激活下一节点；
- 在本地提交已验证且范围清楚的变更。

## 遇到重大决策时停止

以下情况需要用户选择：

- 目标、用户、范围或验收标准发生实质变化；
- 架构将改变持久数据、隔离、隐私、权限、互操作性或长期运行方式；
- 工具带来持续费用、限制性或不明确的许可证、遥测、云端数据传输或供应商锁定；
- 要求互相冲突，且没有安全、可逆的默认选项；
- 新的真实证据推翻了已接受设计。

停止时给出证据、可选方案、取舍、建议，以及一个需要用户回答的明确问题。

## 遇到权限边界时停止

- 安装或修改全局插件、Skill、Hook、受信任程序或持久机器配置；
- 请求凭据、令牌、账号变更、付费服务或超出既定边界的数据传输；
- 执行未获授权的远端推送、PR、发布、生产部署、外部消息或第三方协调；
- 因连接器或 CLI 能力不足改用用户浏览器登录态，但用户尚未允许；
- 执行破坏性或难以恢复的文件、数据库、迁移、历史或基础设施操作。

请求应尽量小，并说明动作、目标、持久性、外部影响和回滚。权限被拒绝后不得绕过。

## 复用同一节点的授权

同一活动节点内，用户已明确批准的同类动作不重复询问。复用仅适用于目标、动作类别、数据类别、成本范围、持久性和外部影响均未改变的后续动作。

不得把一次授权推广到不同类别的新数据或新成本范围。出现新数据类别、任何新增或扩大成本、不同的外部接收方、持久性变化、权限扩大，或转入新节点时，必须请求新授权。授权措辞不清楚时，按未获授权处理。

## 证据登记、条件授权与副作用

触发：收到用户截图、原件、人工决定或外部结果。动作：在 `.delivery/state.md` 先登记最小证据回执，再分析、设计或执行副作用。方法：写 `received_at`、`source_ref`（不可持久保存则 `needs-source`）、范围、直接观察、限制和未决；只有获授权时才复制原件到证据槽。判据：后续结论能追溯到来源，事实与推断分开。失败：标记 `needs-source`，不得把推断写成已证实事实。证据：回执本身及获授权的证据槽引用。

新会话或新活动节点复用既有用户或外部证据，也触发本门；若旧回执缺少 `source_ref` 或 `needs-source`，先补录，随后才能用它支持实施、部署或外部写入。

授权类别必须分开：证据登记、可逆本地实验、远端部署或服务重启、外部持久数据写入、导入/激活/发布。前一类不授权后一类。`先检查并反馈`、`检查后再继续` 等条件性措辞只授权检查和反馈；报告已被用户接收并明确同意下一动作前，不得实施、部署或写入外部状态。

预实验即使已部署也不是完成。登记目的、变更版本、未证明的验收条件、回滚和禁止推导的结论；未满足已批准设计时，不得称为“已上线”、实现完成或后续导入/激活的依据。

## 遇到证据门时停止

- 必需的真实样本、设备、浏览器状态、用户行为、数据集、账号、服务或类生产环境不可用；
- 完整验证命令失败；
- 只有削弱验收标准才能让测试通过；
- 准确率、延迟、隐私、安全或可靠性门槛无法测量。

此时不能把阶段标为完成。记录现有证据、缺失证据、已经穷尽的安全工作，以及准确的解除条件。

## 停止时写出一行可见理由

停止的回复里必须写出一行停止理由，只能从封闭清单选择：

```text
停在这里，因为：<等用户决断 / 等用户机器上的执行结果 / 需要新授权 / 需求有多种合理解释需先厘清>
```

写不出来就不许停，包括刚刚宣布了要做某事的时候。这一行不是闸门而是可见性机制：它把「零产出但消息正常」变成「该有的那行理由不在」。验收标准不是「不再过早停止」，而是「每次停止都能被一眼判断有没有道理」。

用户若另有节奏偏好，那约束的是交接的内容（一次给几组命令），不是回合边界。两件事混同会产生「用一句『我现在开始做』当交接然后停下」的稳态。

## 提交、远端发布与脱敏门

提交前检查工作树、暂存区和完整 Git 历史。范围至少包括私钥、令牌、密码、云凭据、连接串、认证文件、会话 Cookie、真实个人信息、机器专属路径，以及带身份或权限信息的命令输出。

提交元数据同样在范围内。作者与提交者身份随提交一起推送，只扫描文件内容查不到它，需要单独检查全部提交的作者与提交者地址。

触发：执行 `git commit` 前。动作：检查候选提交消息的标题、正文和 trailer，不只扫描既有历史。候选提交消息来自 `-m`、`-F`、编辑器或 Agent 自动生成时都一样处理。会话、分享、聊天或其他不透明协作链接不得写入提交元数据；`Claude-Session` 一类 trailer 也不得写入提交元数据。

方法：先把将要提交的精确文本作为草稿审阅，重点检查 URL、`session`、`share` 和平台名组合；只保留解释变更所必需的、领域中立的文本。判据：候选消息不含会话/分享链接或其 trailer，且不依赖链接才能理解。失败：中止本次提交，删除链接或改写为中立原因，重新检查；若已推送，按历史暴露流程记录并请求清理方案的明确授权。证据：记录检查时间、消息来源、命中类型和处置，不记录链接值。

提交前先确认本次提交实际生效的身份，不要假设它等于项目策略。身份由当前会话与运行时的环境决定：仓库自身可能没有配置，全局配置可能属于另一个用途，运行时也可能通过环境变量注入自己的身份。跨项目、跨运行时或换一台机器继续同一个仓库时，生效值会跟着变，而没有任何环节会提醒你它变了。

做法是提交前读出生效值并与项目覆盖层的作者身份策略核对。`git var GIT_AUTHOR_IDENT` 会把配置与环境变量注入一并算进去，未配置时直接报身份未知。不一致时用单次提交级参数覆盖，例如 `git -c user.name=... -c user.email=... commit`，不修改用户的全局配置。

同一个仓库的历史里出现多组不同身份，就是这一步从未执行过的直接证据。

不得提交真实秘密作为测试样本。测试只能使用明显无效的占位值，并避免采用会被误认为可用凭据的完整格式。扫描工具可用时使用专用秘密扫描器；不可用时使用仓库搜索和 Git 对象检查作为降级，并明确覆盖限制。

发现秘密时：

1. 立即停止提交和推送，不在回复、日志或修复提交中重复秘密。
2. 先撤销或轮换可能仍有效的秘密，再清理当前文件。
3. 已进入 Git 历史的秘密不能靠普通新提交删除。需要选择历史重写、建立干净的新根提交或新仓库。
4. 历史重写、删除旧远端引用和强制推送会影响协作者，属于破坏性远端操作。必须说明备份、影响、重新克隆要求和验证方法，并取得明确授权。
5. 已经推送到公开托管平台的历史，重写加强制推送不足以清除。旧提交仍可按 SHA 访问，也留在克隆、复刻和 PR 引用里。要真正清除需要平台侧介入或删除并重建仓库；决定前先向平台一手文档核实当前行为。
6. 完成清理后重新扫描工作树、暂存区、全部分支和标签，再创建全新提交。

如果只发现公开用户名、公开仓库地址或文档示例，不要误报为秘密。账号标识是否需要匿名化由项目公开范围决定。扫描报告只记录文件、提交、秘密类型和处置状态，不保存秘密值。

## 独立审阅失败恢复门

触发：独立审阅报告 Critical 或 Important 发现。动作：把该发现设为唯一活动节点，复现、最小修复并重新独立审阅；继续禁止未通过门所保护的部署、外部写入、导入、激活或发布。方法：记录发现、受影响范围、复现命令、修复与重审证据；在长验证或重审前确认运行余量，余量不足或不可确认时先记录可恢复交接（活动发现/证据、已完成验证、冻结副作用、唯一恢复动作、解除条件）。判据：发现被复现并修复，相关测试和复审通过。失败：只有新决策、新权限或真实证据缺失时暂停，并写出本门规定的可见停止理由及解除条件；额度耗尽不等同完成。证据：审阅报告、复现、修复和重审记录。

未解决的 Critical/Important 发现不得成为活动节点的最后一项工作或把会话标为完成；审阅发现本身不是暂停理由。

## 最终审阅新鲜度门

触发：一次独立审阅后，代码、运行配置或交付包发生变化。动作：在部署、发布或完成声明前，对最终产物重新独立审阅。判据：审阅对象与将部署、发布或宣称完成的精确版本一致。失败：旧审阅、测试、扫描、自审或旧版本现场验证均不通过本门；已部署旧版本时，记录版本差异，不把旧现场结论用于新版本。证据：最终版本标识和新的独立审阅记录。

### 输出脱敏（运行诊断、探针或状态命令时）

工具输出会原样进入会话与持久记录。运行可能接触凭据的命令（探针、状态检查、日志查看、读配置）前，先核对输出遮蔽策略：凭据值脱敏后才进入上下文，值不得原样出现，键名与结构可留。判据：此类输出不含真实凭据值。诊断结果**默认不落盘**；确需归档时，先脱敏，再写入用户批准且权限合适的位置，并登记保存期限。落槽不等于安全：项目状态区可能被文件同步，含凭据值的内容不得因落入槽位而免于脱敏；槽位不是秘密保险箱，归档也须先脱敏。

发现输出已含真实值（即使脚本声称已遮蔽），按「已泄露」处置：

1. 不重复值：回复、日志、记录中不复制真实值。
2. 立即列入轮换：已泄露的密钥、令牌列入轮换清单，轮换执行须授权。
3. 清理残留：删除落到临时文件、服务器文件的泄露副本并复核。
4. 登记：记录泄露面（哪些会话/文件/机器）、处置与残余。

### 通用性检查

秘密扫描之外还有一道独立检查，两者范围不同，不能互相替代。上面那条「不要误报为秘密」只约束秘密扫描，不豁免这一道。

这**不是安全问题**，是可复用性问题。通用 Skill 带着某一个项目的世界走，会污染它服务的其它每一个项目。判据不是「会不会泄密」，而是：**把这个仓库交给一个完全不相干的项目，读起来会不会莫名其妙。**

范围：用户的基础设施名称、同步工具、服务器主机名、产品名、仓库名，以及只属于某个项目的业务领域词汇。

方法分三层，因为单靠任何一层都不够：

1. 通用形态用测试自动扫描：私有网段地址、用户目录路径、邮箱。写成测试而不是清单，扫描器本身才不会变成泄漏点。
2. 具名词用项目覆盖层的禁用词清单。这些词本身就是项目事实，不写进通用仓库。
3. 领域词汇只能人工过。本次新增或改写的经验条目、示例和触发场景逐条确认领域中立：写清失败模式和判据，不写它发生在哪个业务上。**秘密扫描抓不到它，正则也抓不到它**，只有读一遍能抓到。

发现时不按秘密流程处理：不需要轮换，不需要停止一切。改写成领域中立描述或占位符，重跑测试，正常提交。已进入 Git 历史的，历史重写仍是独立权限门；重写前先确认文档里有没有引用提交 SHA，重写会让这些引用全部失效。
