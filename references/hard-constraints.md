# 硬约束

本页是 H1–H6 的唯一全文。核心、门控和启动块只引用编号，不复制规则文字。每条硬约束都配一个[机械预检](preflight.md)检查；检查失败等同对应门失败：不得暂存、提交、推送或宣告完成，只能修复后重跑。没有检查的规则不属于本页。

| 编号 | 规则 | 机械检查 |
|---|---|---|
| [H1](#h1) | 证据颗粒度：只登记门结论、生产或现场变更、失败根因 | k, l |
| [H2](#h2) | 复审上限：同一改动最多 2 轮，第 3 轮须负责人点名 | m |
| [H3](#h3) | 状态文件格式：三句话开头、完整句子、编号带含义、≤80 行 | j, e |
| [H4](#h4) | 授权作用域：每条授权写适用范围，新任务不继承 | j |
| [H5](#h5) | 规则必须有检查：第二次违反就升级为带检查的硬约束 | n |
| [H6](#h6) | 沿主线开发：除非明确要求，多任务用 worktree，不开新分支 | o |

运行方式：`python -B -X utf8 <skill>/references/preflight.py --root . --json`。首次 `git add` 前、每次提交前（`--staged`）和完成声明前运行。检查 l 默认只提示（warn），其余默认阻断（block）；项目只能在决策登记里写明理由后调整严重级别。

<a id="h1"></a>
## H1 证据颗粒度

规则：事实或证据条目只登记三类，并用标签标明：`[门结论]`、`[变更]`（生产或现场变更）、`[根因]`（失败根因）；英文用 `[gate]`、`[change]`、`[root-cause]`。每条写登记日期 `YYYY-MM-DD`；复审结论写 `第 N 轮`。界面、文案、样式微调和单页修正只写提交信息：不新增条目、不升基线版本、不新建证据文件。

检查：k 检查新增或改动的证据行有无标签、日期和复审轮次；本批改动全部命中 `evidence.minor_paths`（默认样式表、`locales/`、`i18n/`，项目补充界面文案路径）时，新增条目、基线改版或新建 `evidence.files` 下的文件都阻断；基线版本变化却没有新条目或新决策也阻断。l 统计每个日期的条目数，超过 `evidence.daily_limit`（默认 5）时提示逐条复核。

失败时：删掉不属于三类的条目，把内容写进提交信息；不能靠改写标签通过。

<a id="h2"></a>
## H2 复审上限

规则：同一改动的独立复审最多 2 轮。每轮开始前在状态的「复审轮次」段登记 `- <改动名称>：第 N 轮；点名：无。`，证据条目同样写轮次号。需要第 3 轮时停下，按[停止理由](gates.md#stop-reason)写「等用户决断」，把两轮的发现和证据交给负责人；负责人点名后，把该行改为 `点名：<负责人与原始回执>`，再开始第 3 轮。之后每多一轮都重新点名。

检查：m 读取状态的「复审轮次」段；段落缺失、或任一行轮次大于 2 而点名为空或为「无」时阻断，提示「stop here」。

失败时：停止复审，不得以修复小问题为由自行开第 3 轮。本条限定[独立审阅失败恢复门](gates.md#review-failure-recovery)的重审循环。

<a id="h3"></a>
## H3 状态文件格式

规则：状态文件第一个二级标题固定为 `## 三句话`，其中恰好三项，依次是 `现在在：`（现在在哪个节点）、`下一步：`（下一步做什么）、`在等：`（在等谁或等什么）。正文用完整句子，每行以句号、问号或叹号结尾；禁止内部速记，默认禁用 `→`、`=>`、`->`、`TBD`、`w/`、`&&`（代码片段内除外）。提到任何编号都同时写含义：写成「编号（含义）」，或在行首定义「- 编号 含义」。全文不超过 80 行。模板见[状态模板](../assets/harness-state.template.md)。

检查：j 检查三句话段、完整句子、速记词、编号含义和授权段；e 检查行数（`limits.record_max_lines`，默认 80）。未填写的模板占位符按空值处理，所以原样复制的模板不能通过。

失败时：按提示逐行改写；超出 80 行时把历史和证据明细移到各自的唯一入口，不拆成第二份状态文件。

<a id="h4"></a>
## H4 授权作用域

规则：状态的「授权与作用域」段里，每条授权写明 `适用：<轮次或任务>`。新任务不继承旧授权：段内必须有一行 `不在该授权内：`，列出当前任务不得做的动作。转入新任务时，只有 `适用` 已列出该任务的授权继续有效，其余只作历史。

检查：j 检查授权段存在、每条授权都有 `适用：`、`不在该授权内：` 有内容。

失败时：补写适用范围；范围不清时按未获授权处理并请求新授权。本条补充[复用同一节点的授权](gates.md#authorization-reuse)。

<a id="h5"></a>
## H5 规则必须有检查

规则：每条硬约束必须配一个机械检查。没有检查的规则第二次被违反时，必须升级为带检查的硬约束，不能再追加文字。规则改动按下节登记决策。

检查：n 检查决策登记：每条决策有含义、类型、规则、补充或取代、依据；类型为硬约束时检查不能为空；违反次数达到 2 且没有检查时阻断；规则文字含无法判定的词时阻断；执行文件引用的决策编号必须存在。本 Skill 自己的规则表由仓库测试核对：上表每一行的检查都必须是 preflight 已有的检查。

失败时：先写检查，再登记规则；写不出检查的规则只能作为说明，不能称为硬约束。

<a id="h6"></a>
## H6 沿主线开发

规则：除非负责人明确要求开分支，多任务并行时用 worktree 沿主线开发，不新建本地分支：

1. `git worktree add --detach <路径> <主线>` 建立分离头指针的工作树。
2. 在该工作树内提交；完成后在主工作树运行 `git merge --ff-only <提交>` 快进主线。
3. 不能快进时，在该工作树内 `git rebase <主线>` 后再快进；有冲突时停下报告。
4. `git worktree remove <路径>` 清理工作树。

负责人要求开分支时，先登记决策，再把分支名加入 `branches.allowed`。接入既有项目时，已存在的分支逐个列入 `branches.allowed` 并注明接入前已存在。

检查：o 列出本地分支，不在 `branches.allowed`（默认 `main`、`master`）中的分支阻断。

失败时：把新分支上的提交快进或变基到主线后删除该分支；删除分支需要相应权限时按门控请求。

## 规则修订机制

- 登记：规则的新增、补充和取代由负责人决策登记，编号为 D 编号，默认位置 `.delivery/decisions.md`，格式见[决策模板](../assets/decisions.template.md)。规则表只引用决策编号，不在多个文件里复制全文；执行文件（AGENTS.md 等）只放可执行条目，并指向决策编号。
- 关系与依据：每条决策写明补充或取代了哪条旧规则，以及依据（审阅报告或事实编号）。
- 可判定：规则文字不用「适度」「必要时」「酌情」「尽量」「适当」「视情况」「合理」这类无法判定的词，改写成阈值、清单或可观测事件；检查 n 会阻断这些词。
- 版本：基线只因门结论、生产或现场变更、失败根因或新决策改版；纯措辞调整不升版本，检查 k 会阻断无依据的改版。
- 本 Skill 自己修订规则时，在下方修订记录里写明补充或取代与依据，并同步双语文本。

格式化代码的标准流程不是硬约束，见[格式化](formatting.md)。
